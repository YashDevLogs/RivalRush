🧠 1. High-Level Architecture Overview

This is a 2D side-scrolling multiplayer race game built with Unity + Netcode for GameObjects (NGO). The architecture is a hybrid of four patterns: Event-Driven core (GameEvents), Component-Based player entity decomposition (Model/View/Controller), Strategy Pattern AI, and a light Singleton layer for manager access.

The key architectural insight is the strict interface contract layer: IPlayerController, IPlayerEntity, IHealth, IInputSource, IPowerUpEffect. This layer is what allows human players, AI players, and network-replicated objects to share the same systems without coupling.

Architecture Style
  • Event-Driven — GameEvents static hub decouples all cross-system communication
  • Component-Based — PlayerController, PlayerModel, PlayerView, PlayerHealth are separate components
  • Strategy Pattern AI — IAIDecisionStrategy with 4 concrete personalities
  • Singleton Managers — GameManager, RaceManager, LobbyManager, MultiplayerManager, ProjectilePool, VFXPool
Core Systems
  • Game Loop — RaceManager (NetworkBehaviour), TickManager
  • Player — PlayerController, PlayerModel, PlayerView, PlayerHealth
  • Input — IInputSource, HumanInputSource, AIInputSource
  • Networking — LobbyManager, MultiplayerManager, NetworkPlayerSpawner
  • AI — AISensor, AIContext, AIDecisionSystem, Strategy classes
  • Power-Ups — PowerUpController, PowerUpDefinition, ProjectilePool, VFXPool
  • UI — LobbyUI, RaceResultUIController, KillFeedManager, CameraFollow2D
  • World — FinishLine, Checkpoint, Hazard

How the systems layer together

There are three conceptual layers:

  1. Infrastructure Layer — GameEvents (static event bus), TickManager (deterministic timing), CharacterConfig (ScriptableObject data), object pools (ProjectilePool, VFXPool). These are stateless or near-stateless utilities that the rest depends on.
  2. Session Layer — LobbyManager (NetworkBehaviour, DontDestroyOnLoad), MultiplayerManager (MonoBehaviour, DontDestroyOnLoad), NetworkPlayerSpawner. These manage the lifecycle of a networked session from lobby to race end.
  3. Gameplay Layer — RaceManager, GameManager, PlayerController, PowerUpController, AI system, World objects. These exist only within a race scene and are destroyed/reset between sessions.

🧩 2. System Breakdown

🏁
Race / Game Loop System
Owns race state machine and coordinates all players
NetworkBehaviour Singleton

Key Classes: RaceManager, GameManager, TickManager

  • RaceManager is a NetworkBehaviour singleton. It owns the race state machine: Waiting → Countdown → Race → Finished. Uses two NetworkVariables: raceStartTime (double, for synchronized countdown) and raceStarted (bool). The countdown is timestamp-based — server sets raceStartTime = NetworkTime + 3s, all clients read it in Update() and display the same countdown independently.
  • GameManager is a thin scene-level singleton that listens to GameEvents.OnRaceFinished — a hook for future analytics/progression systems. Currently it does nothing but log.
  • TickManager sets Time.fixedDeltaTime = 1f / tickRate (default 60). All gameplay timing — jump buffers, coyote time, wall cling duration, slide duration — is expressed in ticks, not seconds. This makes gameplay deterministic and frame-rate independent.
🧑
Player System
MVC decomposition of human player entity
MVC NetworkBehaviour

Key Classes: PlayerController, PlayerModel, PlayerView, PlayerHealth, PlayerMarker, PlayerIdentity, PlayerInputHandler

  • PlayerController is the heart — a sealed NetworkBehaviour that implements both IPlayerController and IPlayerEntity. It handles physics (Rigidbody2D), all player states, wall cling, jumping, sliding, air diving, and finish-race state. All timing uses ticks via TickManager.
  • PlayerModel is a pure data container — holds all mutable runtime state (CurrentRunSpeed, IsGrounded, JumpsLeft, State, tick counters) and proxies read-only config from CharacterConfig ScriptableObject. No logic, just data.
  • PlayerView is a thin Animator wrapper — exposes UpdateMovement(), TriggerJump(), TriggerDie(). No logic, just Animator param calls.
  • PlayerHealth drives the Dead → Respawning → Invincible → Alive lifecycle using a state enum + float timers (no coroutines — deliberate perf decision noted in comments). Handles VFX via VFXPool.
  • PlayerMarker is a NetworkBehaviour that sets IsLocal = IsOwner on spawn. It is the authority on "is this the local player?". Fires GameEvents.RaiseLocalPlayerSpawned() once on spawn. PlayerMarker.Local is a static reference used by camera and UI.
  • PlayerInputHandler polls its IInputSource in LateUpdate() and routes to controller methods. Gating: checks RaceManager.CanMove() and PlayerMarker.IsLocal before allowing any input through.
🎮
Input System
Abstracts human vs AI input behind a common interface
Interface Pattern

Key Classes/Interfaces: IInputSource, HumanInputSource, AIInputSource, IInputDriver, AIInputDriver

  • IInputSource exposes four bool/float properties: Horizontal, JumpPressed, SlidePressed, PowerUpPressed. Both HumanInputSource and AIInputSource implement it, allowing PlayerInputHandler to be completely blind to whether input is human or AI.
  • HumanInputSource uses Unity's new Input System (Keyboard.current): WASD/Arrows for horizontal, Space=jump, LCtrl=slide, E=powerup.
  • AIInputSource polls AISensor (cached physics results), updates AIContext, then asks AIPowerUpBrain (which delegates to AIDecisionSystem) for jump/slide/powerup decisions.
  • IInputDriver is a legacy/alternative interface (slightly different shape — no SlidePressed). AIInputDriver implements it but appears to be an older path compared to AIInputSource. Both exist in the codebase — worth cleaning up.
🌐
Networking / Multiplayer System
Session management, lobby, and player spawning over NGO
Unity NGO

Key Classes: LobbyManager, MultiplayerManager, NetworkPlayerSpawner, LobbyPlayerData, PlayerInputData, TickManager

  • LobbyManager is the session brain. It's a NetworkBehaviour with DontDestroyOnLoad. It owns a NetworkList<LobbyPlayerData> (replicated lobby state), manages player ready status, fills missing slots with AI, and orchestrates the scene transition. It also implements the scene-ready handshake: each client calls ReportSceneReadyServerRpc() after loading; only when ALL clients report does the server fire StartCountdownClientRpc().
  • MultiplayerManager is a thin NGO wrapper — StartHost(), StartClient(), and StartGame() (loads the level scene). It lives as a DontDestroyOnLoad singleton so it persists from menu into the race.
  • NetworkPlayerSpawner spawns human players on OnNetworkSpawn (0.5s delayed) and AI players when called by LobbyManager after scene load. Uses a sequential spawn point array.
  • LobbyPlayerData is a blittable INetworkSerializable struct — ClientId, PlayerName (FixedString32Bytes), IsReady, IsAI. This is the source of truth for lobby state on all clients.
  • PlayerInputData is a tick-stamped INetworkSerializable struct (horizontal, jump, tick) — appears designed for client-side prediction/replay, though the current implementation comment says prediction/reconciliation was removed.
🤖
AI System
Perception → Context → Strategy → Decision pipeline
Strategy Pattern

Key Classes: AISensor, AIContext, AIDecisionSystem, AIDecisionStrategyBase, AIPowerUpBrain, AIInputSource, AIPersonality

  • AISensor fires 3 raycasts per physics step (in FixedUpdate): hazard-ahead, wall-ahead, low-hazard-ahead. Results are cached as booleans; AIInputSource reads them in Update(). The comment explicitly notes this is an optimization over per-frame raycasting.
  • AIContext is a pure data DTO — aggregates sensor results, power-up state, race state, and distance to target. Updated each frame by AIInputSource and AIPowerUpBrain.
  • AIDecisionSystem holds a [SerializeReference] IAIDecisionStrategy — this allows the strategy to be set in the Inspector as a polymorphic type. Exposes DecideJump(), DecideSlide(), DecideUsePowerUp().
  • AIDecisionStrategyBase is the abstract base implementing cooldown logic, phase-based power-up scoring, and personality bias. Concrete strategies AggressiveStrategy, DefensiveStrategy, BalancedStrategy, RiskyStrategy only override three floats each: JumpDelayMultiplier, PowerUpPersonalityBias, DangerBias.
  • AIPowerUpBrain is a MonoBehaviour bridge — it updates context with power-up and race state, then delegates to AIDecisionSystem. It gives AI the same HandleJump/Slide/PowerUp API surface as human players.
⚡
Power-Up System
ScriptableObject-defined abilities with pooled projectiles/VFX
ScriptableObject

Key Classes: PowerUpController, PowerUpDefinition, IPowerUpEffect, ProjectilePool, VFXPool, PowerUpContext

  • PowerUpController manages hold/activate/expire lifecycle. Uses a float timer (no coroutines) for expiry — zero allocation. The PowerUpContext it builds on Awake bundles references to IPlayerController, IHealth, IPlayerEntity, Transform, and PowerUpAssets.
  • PowerUpDefinition is an abstract ScriptableObject. Subclasses use nested private sealed class Effect : IPowerUpEffect — a clean factory pattern where the definition creates its own effect. Available power-ups: Revolver, Rocket, Sawblade, Shocker, GroundTrap, Shield, SpeedBoost, Trap.
  • ProjectilePool and VFXPool are pre-warmed Queue-based object pools for all combat effects. Pool sizes are Inspector-configurable. All projectiles use ReturnXxx() instead of Destroy().
  • RaceUtility provides stateless targeting helpers: ResolveRocketTarget (furthest-ahead player), ResolveRandomAheadTarget, ResolveNearestOpponent. Uses RaceManager.GetPlayerEntities() as the authoritative player list.
📺
UI System
Event-driven UI: lobby, race results, kill feed, camera
Observer

Key Classes: LobbyUI, RaceResultUIController, KillFeedManager, CameraFollow2D, PowerUpUIController, CurrencyUI

  • LobbyUI pools PlayerSlotUI objects (MaxPlayers = 4) — no Instantiate/Destroy on lobby changes. Subscribes to LobbyManager.Players.OnListChanged (NGO NetworkList event). Buttons call MultiplayerManager.StartHost/Client and LobbyManager.SetReadyServerRpc.
  • RaceResultUIController subscribes to GameEvents.OnRaceFinished, reads RaceManager.GetFinishOrder(), and builds the results panel. Differentiates local player row with color.
  • KillFeedManager uses a pool + LinkedList of KillFeedEntry items — subscribes to GameEvents.OnPlayerKilled for entries, OnRaceFinished to clear all. Zero alloc at runtime.
  • CameraFollow2D subscribes to GameEvents.OnLocalPlayerSpawned to bind its target (reads PlayerMarker.Local). Implements smooth follow with velocity look-ahead using SmoothDamp. On OnRaceFinished, it damps follow speed and triggers finish zoom.

🔄 4. Execution Flows

A. Game Start Flow (Lobby → Race)

1
Menu — Host/Join
LobbyUI.OnCreateLobby() → MultiplayerManager.StartHost() → NetworkManager.StartHost(). LobbyManager spawns as a NetworkBehaviour and calls AddPlayer() for connected clients.
2
Lobby Ready Up
LobbyUI.OnReadyClicked() → LobbyManager.SetReadyServerRpc(true). Server marks player ready in NetworkList<LobbyPlayerData>. All clients receive OnListChanged and refresh LobbyUI.
3
All Ready → Scene Load
When AreAllPlayersReady(): server calls PrepareAIPlayers() (adds fake LobbyPlayerData entries), sets gameStarting = true, calls MultiplayerManager.Instance.StartGame() → NetworkManager.SceneManager.LoadScene("LevelPrototype").
4
Scene Loaded → AI Spawn
LobbyManager.HandleSceneLoaded() fires (server only). It calls NetworkPlayerSpawner.SpawnAIPlayers(). Human players are spawned by NetworkPlayerSpawner.SpawnAllPlayers() with a 0.5s invoke delay on OnNetworkSpawn.
5
Scene Ready Handshake
RaceManager.Start() on each client calls LobbyManager.ReportSceneReadyServerRpc(). Server accumulates reports. When all N clients report: fires StartCountdownClientRpc() to all.
6
Countdown → Race Start
StartCountdownClientRpc() → RaceManager.StartCountdown(). Server sets raceStartTime = NetworkTime + 3s. All clients read raceStartTime in Update(), display countdown, then transition Countdown → Race when time expires. Fires GameEvents.RaiseRaceStarted().

B. Player Lifecycle Flow

1
Spawn
NetworkPlayerSpawner.SpawnPlayer(clientId) → NetworkObject.SpawnAsPlayerObject(clientId). PlayerController.OnNetworkSpawn registers with RaceManager. PlayerMarker.OnNetworkSpawn sets IsLocal = IsOwner, fires RaiseLocalPlayerSpawned().
2
Input → Movement
PlayerInputHandler.LateUpdate() polls IInputSource. For jump: calls PlayerController.HandleJump() → buffers tick in PlayerModel.LastJumpPressedTick. FixedUpdate() calls TryConsumeBufferedJump() → TryPerformJump() → NotifyJumpServerRpc() → PlayJumpClientRpc() on all non-local clients.
3
Death
Hazard/projectile collision → IHealth.TakeDamage() → PlayerHealth.Die() → disables physics, calls PlayerController.DisableControl(), plays VFX from pool, starts respawnTimer. Sets state = Dead.
4
Respawn
PlayerHealth.Update() counts down respawnTimer → RespawnAt(lastDeathPosition + offset). Re-enables physics, calls EnableControl(), starts invincibility blink cycle (float timer, not coroutine).
5
Finish
FinishLine.OnTriggerEnter2D() (server only) → RaceManager.RegisterFinish() → SyncPlayerFinishedClientRpc(playerObjectId) → PlayerController.OnFinishRace() on all clients. Sets HasFinishedRace = true, ControlEnabled = false.

C. Networking Flow

  • Authority model: Server is authoritative for race state, finish order, and player registration. Clients own their input and locally predict movement. Jump events are server-confirmed via RPC.
  • NetworkVariables: raceStartTime (double) and raceStarted (bool) on RaceManager. LobbyPlayerData in a NetworkList on LobbyManager. All replicated automatically.
  • RPCs: NotifyJumpServerRpc (owner → server) → PlayJumpClientRpc (server → all non-local). ReportSceneReadyServerRpc (all clients → server). StartCountdownClientRpc (server → all). EndRaceClientRpc(ulong[] finishOrder) (server → all). SetReadyServerRpc (client → server).
  • Comment note: Client prediction / reconciliation / rollback was intentionally removed. The code references PlayerInputData (tick-stamped struct) which suggests this was designed for prediction but currently unused for that purpose.

D. UI Flow

  • Lobby UI: LobbyUI.OnEnable → wait for LobbyManager.IsSpawned via coroutine → subscribe to Players.OnListChanged. Button clicks → ServerRpcs on LobbyManager.
  • Race countdown: RaceManager.Update() directly writes countdownText.text — no event, pure polling of raceStartTime NetworkVariable.
  • Race results: GameEvents.OnRaceFinished → RaceResultUIController.ShowResults() → reads RaceManager.GetFinishOrder(), populates panel.
  • Kill feed: GameEvents.OnPlayerKilled → KillFeedManager.HandleKill(KillEventData) → pops pooled entry, formats rich text, shows with lifetime timer.
  • Camera: GameEvents.OnLocalPlayerSpawned → CameraFollow2D.BindToLocalPlayer() → snaps to player then smooth-follows in LateUpdate.

E. AI Perception → Decision → Action Flow (per frame)

FixedUpdate:
  AISensor.FixedUpdate() → fires 3 Physics2D.Raycast → caches hazardAhead, wallAhead, lowHazardAhead

Update:
  AIInputSource.Update()
  → AIContext.UpdateDetection(sensor) — read cached booleans
  → AIPowerUpBrain.UpdateContext(context) — add powerup + race state
  → powerUpBrain.DecideSlide(context) → AIDecisionSystem.DecideSlide() → IAIDecisionStrategy.ShouldSlide()
  → if !slide: powerUpBrain.DecideJump(context) → same chain
  → powerUpBrain.ShouldUsePowerUp(context) — phase-bias + personality-bias score
  → sets JumpPressed, SlidePressed, PowerUpPressed

LateUpdate:
  PlayerInputHandler.LateUpdate() → reads IInputSource flags → calls PlayerController methods

📞 5. Function Call Chains

Chain 1: Human Jump Input → Physics → Network Sync

// LateUpdate
PlayerInputHandler.LateUpdate()
  → CanProcessInput()                          // checks RaceManager.CanMove() AND PlayerMarker.IsLocal
  → inputSource.JumpPressed == true
  → PlayerController.HandleJump()
      → CanProcessLocalInput()                   // same gate again
      → if IsWallClinging: TryPerformWallJump()  // branch A
      → else: model.LastJumpPressedTick = currentTick   // buffer jump
            → TryConsumeBufferedJump(currentTick)

// FixedUpdate
PlayerController.FixedUpdate()
  → TryConsumeBufferedJump(currentTick)
      → checks: grounded OR coyote time OR jumpsLeft > 0
      → TryPerformJump(currentTick)
          → rb.linearVelocity = new Vector2(currentRunSpeed * mult, jumpVelocity)
          → model.JumpsLeft--
          → model.NextAllowedGroundCheckTick = currentTick + grace
          → view.TriggerJump()   // local animation
          → if IsOwner: NotifyJumpServerRpc()    // owner → server
          → OnJump?.Invoke()
          → UpdateState(PlayerState.Jumping)

// ServerRpc handler (on server)
PlayerController.NotifyJumpServerRpc()
  → PlayJumpClientRpc()                         // server → all clients

// ClientRpc handler (on all non-local clients)
PlayerController.PlayJumpClientRpc()
  → if IsLocal: return                              // skip on owner (already animated)
  → view.TriggerJump()                             // show jump on remote copies

Chain 2: Player Crosses Finish Line → Race End → UI Results

// Physics trigger (server only checks)
FinishLine.OnTriggerEnter2D(collider)
  → if !NetworkManager.Singleton.IsServer: return
  → collider.TryGetComponent<IPlayerController>(out racer)
  → RaceManager.RegisterFinish(racer)

RaceManager.RegisterFinish(player)
  → if !raceStarted.Value: return
  → finishOrder.Add(player)
  → ApplyPlayerFinishStateOnce(player)
      → if not yet processed: ApplyPlayerFinishState(player)
          → playerController.OnFinishRace()
              → model.HasFinishedRace = true
              → model.ControlEnabled = false
  → SyncPlayerFinishedClientRpc(playerObjectId)    // replicate on clients
  → if finishOrder.Count == racers.Count: EndRace()

RaceManager.EndRace()
  → currentState = Finished
  → raceStarted.Value = false
  → EndRaceClientRpc(BuildFinishOrderObjectIds())   // array of ulong NetworkObjectIds

// ClientRpc (all clients)
RaceManager.EndRaceClientRpc(ulong[] ids)
  → ApplyFinishOrder(ids)    // resolves NetworkObjects, calls OnFinishRace on each
  → GameEvents.RaiseRaceFinished()
      → GameManager.HandleRaceFinished()        // logs
      → RaceResultUIController.ShowResults()    // shows panel
      → KillFeedManager.ClearAll()             // clear kill feed
      → CameraFollow2D.OnRaceFinished()        // damp + zoom

Chain 3: Pickup → Activation → Power-Up Effect

// Player walks over pickup
RandomPowerUpPickup.OnTriggerEnter2D(collider)
  → collider.TryGetComponent<PowerUpController>(out ctrl)
  → ctrl.Pickup(definition)
      → heldDefinition = definition
      → GameEvents.RaisePowerUpPicked(definition.id)
      → OnPowerUpChanged?.Invoke(id)    // → PowerUpUIController updates icon

// Player presses E (or AI decides to use)
PlayerInputHandler.LateUpdate() → inputSource.PowerUpPressed
  → PlayerController.HandlePowerUp()
      → powerUpController.Activate()
          → DeactivateCurrentEffect()  // clear any lingering effect
          → activeEffect = heldDefinition.CreateEffect()   // factory
          → activeEffect.Activate(context)
          → if duration > 0: effectTimeRemaining = duration  // float timer, no coroutine
          → GameEvents.RaisePowerUpActivated(id)

// Example: SpeedBoost
SpeedBoostPowerUpDefinition.SpeedBoostEffect.Activate(ctx)
  → ctx.PlayerController.ModifyMaxRunSpeed(speedMultiplier)   // e.g. 2×

// Timer expires (PowerUpController.Update)
effectTimeRemaining -= Time.deltaTime
→ if <= 0: DeactivateCurrentEffect()
    → activeEffect.Deactivate()
        → ctx.PlayerController.ResetMaxRunSpeed()
    → GameEvents.RaisePowerUpExpired(id)

Chain 4: Player Death from Projectile

// e.g. RocketController hits player
RocketController.OnTriggerEnter2D(other)
  → other.TryGetComponent<IPlayerEntity>(out target)
  → if !target.IsTargetable: return
  → target.IsTargetable: checks !HasFinishedRace, activeHierarchy, !IsInvincible, rb.simulated
  → other.TryGetComponent<IHealth>(out health)
  → health.TakeDamage(1)
  → GameEvents.RaisePlayerKilled(new KillEventData(killer, victim, PowerUpId.Rocket))
      → KillFeedManager.HandleKill(data)   // shows "X killed Y with Rocket"

PlayerHealth.TakeDamage()
  → if IsInvincible: return
  → Die()
      → IsInvincible = true           // prevent double-kill
      → state = Dead, respawnTimer = delay
      → powerUpController.ClearActiveEffects()
      → VFXPool.Instance.GetDeathSmoke(pos)  // pooled VFX
      → rb.simulated = false          // kill physics
      → controller.DisableControl()
      → view.TriggerDie()             // death animation

// respawnTimer counts down in Update → RespawnAt(lastDeathPos + offset)

⚙️ 6. Design Patterns Identification

Pattern Where Used Implementation Quality
Observer / Event Bus GameEvents static class Excellent. Custom Add/Remove with duplicate-subscription guard. Individual invocation loop catches and logs exceptions per-subscriber without killing others. [RuntimeInitializeOnLoadMethod] clears statics on domain reload — critical for domain-reload safety in tests. OnAnyEventRaised hook for global debug tracking.
Strategy AI: IAIDecisionStrategy → 4 concrete strategies Good. [SerializeReference] allows Inspector selection. Abstract base holds all timing logic; strategies only override 3 bias floats. Adding new personality = 5 lines of code.
Factory Method PowerUpDefinition.CreateEffect() Clean. Each ScriptableObject definition creates its own IPowerUpEffect as a nested private class. Zero coupling between pickup and effect.
Object Pool ProjectilePool, VFXPool, KillFeedManager, LobbyUI Consistent and thorough. Pre-warmed Queue pools across projectiles, VFX, kill feed entries, and lobby slots. Pool sizes configurable in Inspector. All return via explicit ReturnXxx() methods. VFXEntry uses self-return pattern.
Singleton RaceManager, GameManager, LobbyManager, MultiplayerManager, TickManager, ProjectilePool, VFXPool Acceptable but over-used. Most implement correct duplicate-destruction guard. LobbyManager and MultiplayerManager use DontDestroyOnLoad correctly. The heavy reliance on static Instance access (especially RaceManager.Instance in PlayerController, AIPowerUpBrain, RaceUtility) creates hidden dependencies.
MVC / Component Decomposition PlayerController + PlayerModel + PlayerView Well-executed. Model is pure data, View is pure presentation, Controller owns all logic. CharacterConfig ScriptableObject keeps designer-tunable values separate from runtime state in Model. Clean separation of concerns.
State Machine PlayerState enum + UpdateState(), RaceState enum, HealthState enum Implicit state machines. Not formal FSM classes — just enums with branching in Update/FixedUpdate. Works fine at this scale but could become hard to maintain if states grow.
Interface Segregation IPlayerController, IPlayerEntity, IHealth, IInputSource, IPowerUpEffect, ICheckpoint, IHazard Strong. The interface layer is the architectural backbone. AI and human players are fully interchangeable to RaceManager, RaceUtility, PowerUpController, and Hazard. Adding a new player type means implementing 2 interfaces.
Template Method AIDecisionStrategyBase with abstract bias properties Clever use. All timing and scoring logic in base class; personality just overrides floats. Strategy pattern at the composition level, Template Method at the inheritance level.

Tight Coupling / Unsafe Dependencies

⚠ Singleton Sprawl

RaceManager.Instance is accessed from: PlayerController, PlayerInputHandler, AIPowerUpBrain, AIContext, RaceResultUIController, RaceUtility, FinishLine. If RaceManager is null (scene not loaded, wrong scene), all of these silently or noisily fail. Defensive null checks are present throughout but it's a hidden dependency.

⚠ PlayerMarker.Local — Static Mutable Reference

PlayerMarker.Local is a static mutable reference set in OnNetworkSpawn. CameraFollow2D reads it on spawn event. If two PlayerMarker objects claim IsOwner = true (shouldn't happen but edge cases exist), the second one is destroyed but static may be stale. Low risk in practice but architecturally fragile.

🔴 Kill Feed Data — No Network Authority

GameEvents.RaisePlayerKilled is called locally (presumably on the server or on the killing client). The kill feed on all clients needs to see this event, but there is no [ClientRpc] wrapping it. Unless the projectile logic always runs server-side and the event fires from a ServerRpc flow, clients may miss kill events. This is a potential multiplayer correctness gap.

✅ Tick-Based Timing

All gameplay timing (jump buffer, coyote time, wall cling, slide, ground grace delay) uses TickManager.CurrentTick integers instead of Time.time floats. This eliminates float precision drift and makes gameplay reproducible regardless of frame rate variation.

✅ GameEvents Domain Reset

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)] clears all static event delegates. This prevents test pollution and stale subscribers across domain reloads in the Editor — a significant operational quality-of-life feature.

🧱 8. Code Quality & Architecture Evaluation

Strengths

✅ Interface Abstraction Layer

The IPlayerController / IPlayerEntity / IHealth / IInputSource contracts are thorough and consistently used. This is the strongest architectural decision in the codebase.

✅ Zero-Alloc Runtime Paths

Comment evidence throughout: coroutines replaced with float timers in PlayerHealth, invincibility blink is timer-driven, PowerUpController expiry is a float countdown, KillFeedManager is pre-warmed. Shows performance discipline.

✅ AI Architecture Extensibility

Adding a new AI personality is 4 lines: create a class extending AIDecisionStrategyBase, override 3 float properties. The [SerializeReference] approach allows Inspector configuration without code changes.

✅ ScriptableObject Config Pattern

CharacterConfig cleanly separates designer-tunable values from runtime state. PowerUpDefinition as ScriptableObject means new power-ups require no code changes — just a new asset.

✅ Scene Ready Handshake

The ReportSceneReadyServerRpc pattern is correct and explicitly comment-documented as fixing a previous race condition (timer-based vs confirmed). All clients guaranteed in scene before countdown starts.

Issues & Risks

⚠ Duplicate Input Interface

Both IInputSource and IInputDriver exist with overlapping purposes. AIInputDriver uses the older interface. This dual-path could cause confusion when extending the input system.

⚠ Singleton Reference Network

7+ singleton managers with static Instance access. This makes unit testing difficult and creates load-order dependencies. RaceManager in particular is referenced from too many places.

⚠ NetworkPlayerSpawner 0.5s Delay

Invoke(nameof(SpawnAllPlayers), 0.5f) — hardcoded magic number. If a client loads slowly, they may not be connected when spawning starts. The scene-ready handshake in LobbyManager solves this at the lobby level but NetworkPlayerSpawner bypasses it.

🔴 KillFeed Not Networked

GameEvents.RaisePlayerKilled is local-only. Kill events from server-side projectile collisions won't reach other clients' kill feeds unless wrapped in a ClientRpc. This is a functional multiplayer gap.

⚠ Removed Client Prediction

Comments explicitly state prediction/reconciliation was removed. PlayerInputData struct exists but is unused for prediction. At low latency this is fine; at 100ms+ latency, player movement will feel laggy on the server-authoritative path.

⚠ FinishLine Server-Only Check

FinishLine correctly gates on NetworkManager.IsServer, but PlayerHealth.Die() and Hazard do not have network authority checks — they run on all clients. This means health/death logic runs locally everywhere, which may cause desyncs in a real multiplayer session.

🧠 10. Mental Model for New Developers

Core mental model: This is a 2D platformer race where all players (human or AI) share the same PlayerController + PlayerInputHandler pipeline. The only difference is what implements IInputSource: a keyboard for humans, a raycast-driven decision system for AI. The race lifecycle is controlled by RaceManager (server authority) via NetworkVariables and RPCs. Everything communicates across systems via GameEvents static delegates — if you want to react to something, subscribe to GameEvents; if you want to notify something, raise a GameEvent.

Entry Points — Where Execution Begins

Lobby Scene Entry
  • LobbyUI.OnEnable() — waits for LobbyManager spawn
  • LobbyUI.OnCreateLobby/OnJoinLobby() — first player action
  • LobbyManager.OnNetworkSpawn() — session setup
Race Scene Entry
  • NetworkPlayerSpawner.OnNetworkSpawn() → spawns players
  • PlayerMarker.OnNetworkSpawn() → fires LocalPlayerSpawned
  • RaceManager.Start() → ReportSceneReadyServerRpc()
  • TickManager.Awake() (ExecutionOrder -1000, runs first)

Core Abstractions to Understand First

AbstractionWhy It Matters
IInputSourceThe seam between human and AI. Everything that touches player control goes through this. Understand it first.
GameEventsThe connective tissue. Almost every cross-system interaction goes through here. Trace events to understand data flow.
IPlayerController / IPlayerEntityRaceManager, RaceUtility, and all power-ups use these — not concrete types. Any new player type must implement both.
RaceManager.CanMove()The central gate for all gameplay. PlayerController, PlayerInputHandler both check this before doing anything.
TickManager.CurrentTickAll timing is ticks, not Time.time. Don't use Time.time for gameplay logic — use ticks.

Safe Extension Points

✅ Safe: New Power-Up

Create a PowerUpDefinition ScriptableObject subclass, implement CreateEffect() returning an IPowerUpEffect. Zero changes to existing systems. Add an entry to PowerUpId enum. Done.

✅ Safe: New AI Personality

Create a class extending AIDecisionStrategyBase, override 3 float properties. Add a AIPersonality enum value. Inspector-assignable via [SerializeReference].

✅ Safe: Reacting to Game Events

Subscribe to GameEvents.OnRaceStarted/Finished/PlayerKilled etc. in OnEnable/OnDisable. No coupling to any other system needed.

✅ Safe: New World Interaction

Implement ICheckpoint, IHazard, or IEndPoint. Access IHealth or IPlayerController via TryGetComponent. Raises GameEvents as appropriate.

Risky Areas — Modify With Caution

🔴 Don't touch: RaceManager state machine transitions

The Waiting → Countdown → Race → Finished flow is tightly coupled to the scene-ready handshake, NetworkVariables, and countdown timing. Modifying transition conditions can cause mismatches between server and clients.

🔴 Don't touch: PlayerController FixedUpdate movement

The tick-based jump buffer, coyote time, and ground check logic have subtle ordering dependencies. Breaking the tick contract will cause inconsistent gameplay.

⚠ Be careful: Expanding PlayerHealth's death/respawn

The Dead → Invincible → Alive state machine uses float timers that must be reset correctly. Adding new states requires updating all transition paths including SetInvincible(false) calls.

⚠ Be careful: LobbyManager AddPlayer / AI fill logic

The AI fill logic (PrepareAIPlayers) uses fake ClientIds (ulong.MaxValue - i) that must not collide with real client IDs. The sequence matters: RemoveAI → count humans → add AI. Don't reorder.

Reading Order for a New Developer

  1. Core/GameEvents.cs — understand the event bus before everything else
  2. Core/IPlayerController.cs, IPlayerEntity.cs, IHealth.cs, IInputSource.cs — the contract layer
  3. Game/RaceManager.cs — understand the race state machine and network authority
  4. Player/PlayerController.cs — the most complex single file; read with PlayerModel beside it
  5. Multiplayer/LobbyManager.cs — session lifecycle and the scene-ready handshake
  6. AI/AIInputSource.cs + AIDecisionStrategyBase.cs — how AI plugs into the same input pipeline
  7. PowerUp/PowerUpController.cs + one Definition — understand the ScriptableObject factory pattern
